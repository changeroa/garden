# 🔌 FsProvider: 유니버설 어댑터

`FsProvider`는 우리 아키텍처의 "식자재 공급업체"입니다. 파일이 사용자의 컴퓨터에 있든(`LocalFsProvider`), 멀리 떨어진 서버에 있든(`RemoteFsProvider`), 심지어 가짜 데이터(`MockFsProvider`)이든 상관없이, 상위 레이어(서비스, 상태)에게는 완전히 동일한 방식으로 파일을 제공하는 것이 핵심 역할입니다.

### 왜 필요한가? (The 'Why')

만약 `FsProvider`가 없다면, 우리는 각 파일 시스템 종류별로 코드를 따로 작성해야 합니다.

```typescript
// 😱 안 좋은 예시
if (isLocalFile) {
  const handle = await window.showDirectoryPicker();
  // ... 로컬 파일 처리 로직 ...
} else if (isRemoteFile) {
  const response = await fetch('https://.../files');
  // ... 원격 파일 처리 로직 ...
}
```

`FsProvider`는 이 모든 차이를 숨기고, 하나의 아름다운 인터페이스 뒤에 감춰줍니다. 마치 전 세계 어디서든 쓸 수 있는 '유니버설 여행 어댑터'와 같습니다.

### 계약서: `FsProvider` 인터페이스

이것이 우리가 모든 Provider에게 요구하는 '계약서'입니다. 모든 Provider는 이 약속을 지켜야 합니다.

```typescript
// src/features/file-explorer/providers/FsProvider.ts

interface FsNode { /* ... FsNode 정의 ... */ }

interface FsProvider {
  // 기능 플래그: 이 Provider가 뭘 할 수 있는지 알려줌
  idStability: 'stable' | 'path';
  emitMoveEvents: boolean;

  // 핵심 메서드
  list(path: string, options?: { signal?: AbortSignal }): Promise<FsNode[]>;
  stat(path: string, options?: { signal?: AbortSignal }): Promise<FsNode>;
  
  // 💥 중요: ArrayBuffer를 반환!
  read(path: string, options?: { signal?: AbortSignal }): Promise<ArrayBuffer>;
  readStream?(path: string): Promise<ReadableStream<Uint8Array>>;

  // 쓰기/수정
  write?(path: string, data: ArrayBuffer | Blob, options?: any): Promise<void>;
  mkdir?(path: string): Promise<void>;
  rename?(oldPath: string, newPath: string): Promise<void>;
  remove?(path: string): Promise<void>;

  // 💥 중요: 실시간 변경 감지
  watch?(rootPath: string, callback: (event: FsEvent) => void): Promise<() => void>; // Unsubscribe 함수 반환
}
```

### 핵심 메서드 심층 분석

- **`read(): Promise<ArrayBuffer>`**: 왜 `string`이나 `base64`가 아닐까요?
    - **책임 전가**: Provider는 파일을 '날 것' 그대로 가져오는 책임만 집니다. 이 `ArrayBuffer`를 텍스트로 해석할지, 이미지로 처리할지는 상위 서비스(`FileEnhancementService`)가 결정합니다. 이는 Provider를 더 단순하고 재사용 가능하게 만듭니다.
    - **성능**: 대용량 파일을 `base64`로 인코딩하는 것은 매우 느리고 메모리를 많이 차지합니다. `ArrayBuffer`나 `Blob`으로 직접 다루는 것이 훨씬 효율적입니다.

- **`watch()`**: 왜 필요할까요?
    - **반응성**: `watch`가 없다면, 우리는 "1초마다 폴더를 다시 읽어서 바뀐 게 있나?" 확인(`polling`)해야 합니다. 비효율적이죠. `watch`는 파일 시스템이 "어이, 여기 파일 하나 바뀌었어!"라고 우리에게 알려주는 '푸시 알림'과 같습니다. `LocalFsProvider`는 `FileSystemObserver`나 폴링으로, `RemoteFsProvider`는 WebSocket/SSE로 이를 구현할 수 있습니다.

- **`readStream()`**: 왜 필요할까요?
    - **대용량 파일**: 10GB짜리 비디오 파일을 `read()`로 읽으면 브라우저가 멈출 겁니다. `readStream`은 파일을 작은 조각(chunk)으로 나누어 물 흐르듯이(stream) 처리하게 해줍니다. 유튜브가 비디오 전체를 다운로드하지 않고도 재생하는 것과 같은 원리입니다.

- **`AbortSignal`**: 왜 모든 메서드에 있을까요?
    - 이것은 [[6. Concurrency & Errors - The Safety Net|동시성 제어]]를 위한 '취소 버튼'입니다. 사용자가 폴더를 열다가 다른 폴더를 바로 클릭하면, 이전의 불필요한 요청을 취소해서 낭비를 막고 에러를 방지합니다.
