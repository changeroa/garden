# 🧠 상태 관리: 단 하나의 진실의 원천

`fileExplorerSlice`는 우리 파일 탐색기의 '주방 총괄 매니저' 또는 '중앙 관제탑'입니다. 파일 트리에 대한 모든 정보, 그리고 유저 상호작용에 따른 모든 상태 변화는 **오직 이곳에서만** 관리됩니다.

### 왜 중앙 관리가 필요한가?

만약 각 UI 컴포넌트가 자신만의 상태(`useState`)를 갖는다면?

- `FileTree` 컴포넌트는 `expandedFolders` 상태를, `Toolbar` 컴포넌트는 `selectedFiles` 상태를 가집니다.
- `FileTree`에서 파일 선택을 바꾸면, `Toolbar`는 어떻게 그 사실을 알 수 있을까요? 복잡한 `props` 전달과 콜백 지옥이 펼쳐집니다.
- 앱의 현재 상태를 한눈에 파악하기 어렵고, 버그 추적도 힘들어집니다.

Redux(또는 유사한 상태 관리 라이브러리)를 사용하면, 모든 상태가 하나의 거대한 자바스크립트 객체(`store`)에 저장됩니다. 이것이 **"단 하나의 진실의 원천(Single Source of Truth)"** 원칙입니다.

### `fileExplorerSlice`의 스키마

우리 파일 탐색기의 모든 '진실'은 아래와 같은 구조로 저장됩니다.

```typescript
// src/features/file-explorer/state/fileExplorerSlice.ts

interface FileExplorerState {
  // 데이터의 원본 (정규화된 형태)
  nodes: {
    byId: { [id: string]: FsNode }; // ID를 키로 모든 노드 정보를 저장
    rootIds: string[];              // 최상위 루트 폴더들의 ID
  };

  // ID ↔ 경로 매핑 (ID 안정성 유지를 위해)
  idPathMap: { [id: string]: string };

  // UI 상태 (모두 안정적인 ID를 기준으로 저장)
  expanded: { [id: string]: boolean };
  selected: { [id: string]: boolean };
  activeDirId: string | null;

  // 비동기 처리 상태 (💥 노드별로 관리!)
  statusById: { [id: string]: 'idle' | 'loading' | 'ready' | 'error' };
  errorById: { [id: string]: string | null };
  
  // 동시성 제어를 위한 진행중인 요청 저장소
  inflightById: { [id: string]: AbortController };
}
```

### 핵심 상태 심층 분석

- **`nodes.byId`**: [[2. FsNode & ID Strategy - The Identity Crisis|정규화된 데이터 구조]]입니다. 모든 `FsNode` 객체를 ID를 키로 하는 맵에 저장합니다. 이렇게 하면 특정 노드를 찾거나 업데이트할 때 매우 빠릅니다. `O(1)` 복잡도!

- **`statusById`**: **가장 중요한 UI 상태 중 하나입니다.** `isLoading: true` 같은 단일 상태 플래그를 사용하지 않는 이유가 있습니다.
    - **문제**: 단일 플래그를 쓰면, 폴더 A를 여는 동안 폴더 B를 열 수 없습니다. 앱 전체가 '로딩 중' 상태에 빠집니다.
    - **해결**: 노드별 상태를 사용하면, 폴더 A 옆에만 스피너를 표시하고, 그 동안 사용자는 다른 폴더를 탐색하는 등 다른 작업을 자유롭게 할 수 있습니다. 에러가 발생해도 해당 폴더에만 "실패" 아이콘을 표시할 수 있습니다.

### Thunks: 액션의 오케스트레이터

UI 컴포넌트는 `dispatch(expandNode(nodeId))` 같은 간단한 '의도'만 표현합니다. 실제 복잡한 일은 **Thunk**가 처리합니다.

**`expandNode` Thunk의 가상 시나리오:**

1.  **(시작)** `nodeId`를 인자로 받습니다.
2.  **(동시성 제어)** `inflightById[nodeId]`에 이미 진행중인 요청이 있는지 확인하고, 있다면 `abort()`로 취소합니다. [[6. Concurrency & Errors - The Safety Net|자세히 보기]]
3.  **(상태 업데이트)** `statusById[nodeId]`를 `'loading'`으로 변경합니다.
4.  **(Provider 호출)** `idPathMap`에서 `nodeId`에 해당하는 `path`를 찾습니다.
5.  **(API 통신)** `FsProvider.list(path)`를 호출합니다.
6.  **(결과 처리)**
    - **성공 시**:
        - 받아온 `FsNode` 목록을 `nodes.byId`에 추가/업데이트합니다.
        - `expanded[nodeId]`를 `true`로 설정합니다.
        - `statusById[nodeId]`를 `'ready'`로 변경합니다.
    - **실패 시**:
        - `statusById[nodeId]`를 `'error'`로 변경합니다.
        - `errorById[nodeId]`에 에러 메시지를 저장합니다.
7.  **(정리)** `inflightById[nodeId]`를 정리합니다.

UI는 이 모든 과정을 모르고, 그저 `statusById`가 바뀜에 따라 스피너를 보여주거나 에러를 보여줄 뿐입니다. 역할 분리가 명확해집니다.
