# 🆔 FsNode와 ID 전략: 정체성 위기 해결하기

이 아키텍처에서 가장 중요하고, 가장 먼저 해결해야 할 문제입니다.

### 문제: 파일의 정체성은 무엇인가?

간단한 질문을 해봅시다. 사용자가 `docs` 폴더를 열어둔 상태에서, `report.md` 파일의 이름을 `final_report.md`로 바꾸면 어떻게 될까요?

만약 우리가 파일의 **경로(`/docs/report.md`)**를 파일의 유일한 식별자로 사용한다면, 끔찍한 일이 벌어집니다.

- `expanded: ['/docs']` - 이건 괜찮습니다.
- `selected: ['/docs/report.md']` - **이 파일은 더 이상 존재하지 않습니다!** 선택 상태가 풀려버립니다.
- 만약 `report.md`가 폴더였다면? 그 폴더 안에 열어뒀던 모든 하위 폴더 상태도 날아갑니다.

이것이 '정체성 위기'입니다. 파일의 이름이나 위치(경로)는 바뀔 수 있는 **겉모습**일 뿐, 앱의 상태를 안정적으로 유지하기 위한 **고유한 신분증**이 필요합니다.

### 비유: 이름 vs. 주민등록번호

- **경로(Path)**: 사람의 '이름'과 같습니다. 개명하면 바뀝니다. 동명이인도 있을 수 있습니다.
- **ID**: 사람의 '주민등록번호'와 같습니다. 절대 바뀌지 않는 고유한 값입니다.

우리 앱의 모든 UI 상태(선택, 확장, 로딩 상태 등)는 이 **ID**를 기준으로 저장되어야 합니다.

### 해결책: 이원화(Dual) ID 전략

모든 [[1. FsProvider - The Universal Adapter|FsProvider]]가 완벽한 '주민등록번호'를 발급해주면 좋겠지만, 현실은 그렇지 않습니다. (특히 로컬 파일 시스템은!)

그래서 우리는 Provider의 능력에 따라 두 가지 전략을 모두 사용하는 '이원화 전략'을 사용합니다.

1.  **Provider가 안정적인 ID를 제공하는 경우 (`idStability: 'stable'`)**
    - `RemoteFsProvider`가 백엔드 DB의 UUID를 ID로 주는 경우입니다.
    - 가장 이상적입니다. 우리는 그 ID를 그대로 사용하면 됩니다.

2.  **Provider가 안정적인 ID를 제공 못하는 경우 (`idStability: 'path'`)**
    - `LocalFsProvider`가 대표적입니다. 파일 시스템은 파일에 대한 고유 ID를 제공하지 않습니다.
    - **우리가 직접 ID를 만듭니다**: `id = "workspace-1:/src/components/Button.tsx"` 처럼, 워크스페이스 ID와 정규화된 상대 경로의 조합으로 ID를 생성합니다.
    - **치명적 약점**: 이 ID는 여전히 경로에 의존합니다. 파일 이름이 바뀌면 ID도 바뀝니다.
    - **보완책: ID ↔ 경로 매핑 테이블 관리!**
        - `fileExplorerSlice` 상태 안에 `idPathMap: { [id: string]: string }` 같은 맵을 유지합니다.
        - **앱 내부에서 파일명을 변경/이동할 때**: 우리는 옛날 경로와 새 경로를 모두 알고 있습니다. 이 때, **ID는 그대로 두고** `idPathMap`의 경로만 살짝 바꿔줍니다!
        - 이렇게 하면, 외부에서 보기엔 경로가 바뀌었지만, 우리 앱 내부적으로는 동일한 ID를 유지하여 모든 UI 상태(확장, 선택 등)가 보존됩니다!

### 외부에서 파일이 변경되면?

이것이 가장 어려운 문제입니다. 내가 VSCode에서 파일명을 바꿨을 때 우리 앱이 알아채는 경우입니다.

- `watch` 이벤트가 `moved`를 지원하면(`emitMoveEvents: true`), 위와 동일하게 `idPathMap`을 갱신합니다.
- 지원하지 않으면, "파일 삭제 + 파일 생성" 이벤트로 보입니다. 이 경우, "이름만 같고 위치가 다른 파일을 이동으로 추정"하는 휴리스틱을 사용하거나, 최악의 경우 해당 폴더의 상태를 그냥 초기화하고 사용자에게 다시 열도록 합니다. (완벽함보다 안정성을 택하는 현실적 타협)

### `FsNode`의 구조: 정규화(Normalization)

이러한 ID 기반 상태 관리를 위해, `FsNode`는 다음과 같이 정규화된 구조를 가집니다.

```typescript
interface FsNode {
  id: string;       // 고유 ID (주민등록번호)
  path: string;     // 현재 경로 (이름)
  name: string;     // 파일/폴더 이름
  type: 'file' | 'folder';
  
  parentId: string | null; // 부모 노드의 ID
  childIds?: string[];     // 자식 노드들의 ID 목록 (폴더인 경우)
  
  // ... 기타 메타데이터 (size, mtime 등)
}
```

`children: FsNode[]` 처럼 중첩 구조로 저장하지 않는 이유는, Redux 같은 상태 관리 라이브러리에서 특정 노드 하나만 업데이트하기 훨씬 쉽기 때문입니다. (예: `nodes.byId[id] = newNode`)
