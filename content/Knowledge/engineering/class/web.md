Web Browser란 무엇인가?
	URL을 통해서 필요한 파일의 위치를 알아내고, 이에 대한 Fetch를 요청하고, 이에 대한 응답을 받아 파싱(HTML, CSS를 트리형태의 파일구조인 DOM으로 만들어줌)하고 렌더링(DOM을 화면에 나타나게 해줌)해주는 프로그램.
		URL은 Uniform Resource Locator이다. 모든 타입의 파일들이 동일한 규약 속에서 사용자에게 할당될 수 있게 해준다. 짧게 말해 파일을 찾는 공통 규칙이다.
		DOM : Document Object Model이다. 문서라는 객체가 너무나 거대한 프로그램이어서 모델이라는 표현을 쓴다. 
			Large Languge Model도 포괄해서, 프로그램이라고 부르기엔 너무 거대한 프로그램을 모델이라고 한다? 근데 Document Object가 가져야하는 상태의 표현을 Model이라고 하는 것 아닌가? 헷갈린다.
		DOM 파일과 렌더링을 합친 것을 UI라고 볼 수 있다.

웹 개발자의 역할 : 파일에 대한 Fetch를 요청받고, 이에 대한 응답을 받는 과정의 규칙을 설계하는 것.
	여기서 말하는 파일 : DOM형태가 되기 전의 원시 데이터이다.즉 HTML / CSS / JavaScript이다.
		HTML : Hypertext Makrup Language이다. DOM요소간의 연결(Hypertext), 그리고 각 DOM요소의 구조를 규정(Markup)하는 언어이다.
		CSS : Cascade Style Sheet이다. 상속 규칙이 '폭포수처럼 계단식으로 적용되는 구조'여서 이런 이름이 붙었다고 한다. 거대한 HTML의 전체 스타일이 하나의 큰 물 줄기라고 하면, 그 안에 포함된 DOM 요소들의 스타일로 인해, 물줄기에 여러 분기가 생길 것이다. 이렇게 생성된 여러 물줄기가 폭포의 심상처럼 느껴지기에 Cascade라는 단어를 쓴듯 하다. 
		JavaScript : HTML과 CSS를 사용자가 사용중에 바꿔야하는 일이 많이 생기면서 자리잡게된, 웹에 동적인 요소를 부여하는 표준이 된 언어이다. 
			1. Process in detail : JavaScript에 의해 하이퍼 텍스트나 마크업, 그리고 CSS가 변경되면, 브라우저는 다시 랜더링한다. 다만 JS 프레임워크들은 변경된 내용을 DOM에 반영하고, diff만 찾아서 부분적으로 다시 렌더링 해주는 기능을 한다고 한다. 
			2. 요즘엔 TypeScript를 많이 쓰는걸로 알고 있는데, 이는 자바 스크립트가 덕타이핑 기반의 동적 타이핑 언어, 즉 런타임에서 타입이 결정되는 언어여서 타입 안정성을 위해 TypeScript를 많이 쓴다고 한다.
					“If it walks like a duck and quacks like a duck, then it's a duck.”
					객체가 특정 타입이라고 선언되지 않았어도, 그 타입이 요구하는 행동(메서드, 속성)을 제공하면 그 타입처럼 취급한다.
						그럼 궁금한 점 : 같은 매서드, 속성을 제공하는 두 상이한 클래스가 있으면 어떡하나? -> 같은 메서드·속성을 가진 두 상이한 클래스가 있더라도,  그 함수는 그 둘의 타입을 신경 쓰지 않고 “필요한 행동을 제공하는지”만 보고 파라미터로 받아들인다.
			3. 근데 그럼 왜 애초에 JavaScript를 타입 안정성 있는 언어로 만들지 않았는가? 이는 웹 개발자들이 빠르게 배우고 적응할 수 있는 언어로서 JavaScript가 설계 됐기 때문이다. 이러한 낮은 진입 장벽으로 인해 JavaScript는 웹의 표준이 되었다.
			4. 그 전에는(1990년대 초반) 웹 페이지는 HTML로만 이루어진 정적인 문서였다. 뭔가 동적인 기능이 필요하면, 서버 측에서 CGI 스크립트 같은 것으로 새로운 HTML을 생성해서 다시 유저에게 보내줘야 했다. 즉  JavaScript 이전의 웹은 기본적으로 정적이고, 서버 중심이었던 것이다.
				CGI : Commom Gateway Interface이다.
					Common, Interface : '여러 언어'를 '공통된 방식'으로 연결해준다. 초창기 웹 시대에는 각 '언어'마다 다른 스크립트를 써서 HTML을 만들었다. 근데 각 언어마다 서버와 데이터를 주고받는 방식이 다 달랐다. 그래서 이들을 '하나의 규칙'으로 실행, 입출력 처리하게 해주는 것.
					Gateway : 초기 웹 서버는 DB조회나 계산이 필요한 동적인 페이지는 외부 프로그램한테 생성하도록 요청해야 했다. 이를 주고 받을 수 있는 웹 서버와 외부 프로그램 사이의 관문이 필요했던 것이다.
				그럼 서버사이드 랜더링은 무엇인가? 이는 서버가 HTML을 랜더링해서 클라이언트한테 보내는 방식이다. 이를 통해 사용자는 빠르게 화면을 볼 수도 있고, SEO(Search Engine Optimization)에도 좋다고 한다.
					
		
왜 단순 Javascript보다 WASM & Rust의 조합을 추가했을 때 더 빠른가?
	WASM + Rust는 JS의 비서라고 비유할 수 있을거 같다 DOM 내에서 비용이 큰 연산을 이들에게 외주를 맡기는 것이라고 볼 수 있다. 결정적으로 WASM은 DOM을 직접 조작할 권한이 없다. 반드시 JS를 거쳐야 한다.
