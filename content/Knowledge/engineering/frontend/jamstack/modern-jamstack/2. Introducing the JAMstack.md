### 2장. JAMstack 소개

#### 이름에는 무엇이 담겨 있을까요?

JAMstack은 본질적으로 널리 사용되는 일련의 아키텍처 관행에 이름을 붙이려는 단순한 시도입니다. 이는 광범위한 아키텍처 결정들을 전달하기 위해 우리에게 단 하나의 단어를 제공합니다.

이 용어는 정적 사이트 생성기(static site generators), 단일 페이지 애플리케이션(SPA) 프레임워크, 빌드 도구, 그리고 API 서비스 커뮤니티에 관련된 사람들 사이의 대화에서 탄생했습니다. 우리는 이 각각의 카테고리에서 일어나는 혁신의 상당 부분이 서로 연결되어 있다는 것을 깨달았기 때문입니다.

지킬(Jekyll), 미들맨(Middleman), 메탈스미스(Metalsmith), 캑터스(Cactus), 루츠(Roots)와 같은 성숙한 1세대 정적 사이트 생성기들을 중심으로 전체 커뮤니티가 성장했습니다. 지킬은 깃허브 페이지(GitHub Pages)가 기본적으로 지원하는 정적 사이트 생성기로서 명성을 얻었고, 다른 도구들은 에이전시나 스타트업이 자사 웹사이트 스택의 핵심 부분으로 개발하면서 발전했습니다. 이 도구들은 자신들이 대체한 복잡한 데이터베이스 기반의 콘텐츠 관리 시스템(CMS)으로부터 단순함과 통제감을 되찾아 주었습니다.

동시에 Vue나 React 같은 단일 페이지 앱 프레임워크는 프론트엔드를 백엔드에서 분리(decoupling)하는 과정을 시작했습니다. 이 과정에서 Grunt, Gulp, 그리고 나중에는 Webpack과 Babel 같은 빌드 도구들이 도입되었고, 이들은 모두 자체적인 빌드 파이프라인과 배포 프로세스를 갖춘 독립적인 프론트엔드라는 개념을 확산시켰습니다. 이는 프론트엔드 워크플로에 적절한 소프트웨어 아키텍처를 도입했고, 프론트엔드 개발자들이 사용자 인터페이스(UI)와 인터랙션 계층을 훨씬 더 빠르게 반복 개선할 수 있도록 힘을 실어주었습니다.

웹사이트와 애플리케이션을 구축하는 이러한 접근 방식들이 교차할 때, 새로운 API 생태계가 등장하기 시작했습니다. 스트라이프(Stripe), 디스커스(Disqus), 알고리아(Algolia) 같은 도구들은 API 기반 서비스를 통해 프론트엔드에서 직접 결제, 댓글, 검색 기능을 사용할 수 있게 만들었습니다.

이러한 새로운 소프트웨어 아키텍처의 다양한 조각들을 지칭하는 수많은 용어가 등장하기 시작했습니다. 프로그레시브 웹 앱(PWA), 정적 사이트, 프론트엔드 빌드 파이프라인, 단일 페이지 애플리케이션(SPA), 분리된(decoupled) 웹 프로젝트, 서버리스 함수 등이 그것입니다. 하지만 이 중 어느 것도 콘텐츠 중심 웹사이트와 웹 애플리케이션, 그리고 그 둘 사이의 흥미로운 하이브리드 형태 모두를 아우르는 새로운 아키텍처로의 이동을 진정으로 포착하지는 못했습니다.

JAMstack은 이 모든 것에 이름을 붙였습니다.

오늘날의 웹 개발 환경에서 "스택(stack)"은 한 단계 위로 이동했습니다. 이전에는 스택을 설명할 때 운영체제, 데이터베이스, 웹 서버(LAMP 스택이나 MEAN 스택 등)를 이야기했지만, 새로운 관행의 등장으로 실제 아키텍처의 제약 조건은 다음과 같이 변했습니다.

- 런타임으로서의 브라우저 내 **자바스크립트(JavaScript)**
    
- 앱별 데이터베이스가 아닌 재사용 가능한 **HTTP API**
    
- 전송 메커니즘으로서의 **미리 빌드된(Prebuilt) 마크업(Markup)**
    

이 구성 요소들이 JAMstack의 **JAM**이 되었습니다. 이제 이 각 요소들이 어떻게 진화하여 이 새로운 아키텍처를 가능하게 했는지 살펴보겠습니다.

#### 자바스크립트 (JavaScript)

1995년 5월, 브렌던 아이크(Brendan Eich)가 유명한 '10일간의 코딩 질주'를 통해 자바스크립트의 첫 번째 프로토타입(원래 이름은 모카(Mocha))을 작성했을 때, 이것이 언젠가 역사상 가장 광범위한 퍼블리싱 스택을 위한 가장 중요한 런타임 언어가 될 것이라고 상상한 사람은 거의 없었을 것입니다.

오늘날 자바스크립트는 브라우저 내에서 거의 어디에나 존재합니다(omnipresent). 아이크가 처음 만든 C와 유사한 문법을 가진 스킴(Scheme) 영감의 작은 언어에서, 이제는 세계에서 가장 고도로 최적화된 인터프리터 언어로 성장했습니다. 여기에는 비동기 작업을 위한 고급 구조, 유연한 클래스 및 모듈 시스템, 구조 분해 할당(destructuring assignment)과 같은 우아한 문법 구조, 그리고 웹을 넘어 가장 널리 사용되는 데이터 교환 형식이 된 객체 문법(JSON)이 포함됩니다.

자바스크립트는 단순한 독립 프로그래밍 언어를 넘어, 다양한 자바스크립트 변형을 모든 최신 브라우저에서 실행 가능한 순수 자바스크립트로 변환하는 **트랜스파일러(transpilers)**와, Elm, ReasonML, ClojureScript, TypeScript와 같은 신규 또는 기존 언어를 위한 **컴파일러(compilers)**의 컴파일 타겟이 되었습니다.

여러 면에서 자바스크립트는 썬 마이크로시스템즈(Sun Microsystems)가 자바 가상 머신(JVM)을 만들 때 꿈꾸었던 유니버설 런타임이 되었습니다.

웹을 위한 이 "가상 머신"은 JAMstack의 런타임 계층입니다. 우리가 완전한 애플리케이션을 작성하든 콘텐츠 기반 사이트에 추가 기능을 더하든, 콘텐츠와 프레젠테이션 계층 위에서 동적인 흐름을 만들어야 할 때 타겟으로 삼는 계층입니다. 브라우저가 웹의 운영체제가 됨에 따라, 유닉스(Unix)에 C 언어가 있었던 것처럼 JAMstack에는 자바스크립트가 있습니다.

#### API

월드 와이드 웹(World Wide Web)은 본질적으로 HTTP(HyperText Transfer Protocol)라는 상태 없는(stateless) 프로토콜 위에 구축된 UI 및 인터랙션 계층일 뿐입니다. 웹의 가장 근본적인 개념은 URL(Universal Resource Locator)입니다.

인간으로서 우리는 브라우저에 URL을 입력하거나 웹사이트의 링크를 따라 다른 웹사이트로 이동하는 것에 익숙합니다. 웹사이트나 애플리케이션을 구축할 때 우리는 항상 URL 아키텍처와 구조에 대해 신중하게 생각해야 합니다. 하지만 URL은 브라우저에서 실행되는 프로그램에도 웹에 노출된 모든 프로그래밍 리소스에 도달할 수 있는 힘을 부여합니다.

현대적인 웹 API는 2000년 로이 필딩(Roy Fielding)의 논문 "아키텍처 스타일과 네트워크 기반 소프트웨어 아키텍처의 설계"와 함께 공식적으로 탄생했습니다. 이 논문은 HTTP를 통해 노출된 서비스들을 위한 확장 가능하고 탐색 가능한 아키텍처로서 REST(Representational State Transfer)를 정의한 획기적인 논문입니다.

초기의 웹 API는 서버 측 애플리케이션에서 소비하도록 의도되었습니다. 중개 서버를 통한 프록시나 플래시(Flash) 또는 자바 애플릿(Java Applets, 으악!) 같은 플러그인을 사용하는 편법 없이는, 표준 브라우저에서 실행되는 프로그램이 자신의 도메인 외부의 웹 API와 통신할 방법이 없었습니다.

자바스크립트가 서버 측에서 렌더링 된 웹사이트 위에 소소한 점진적 향상(progressive enhancements)을 수행하는 스크립트 언어에서 완전한 런타임 환경으로 성장함에 따라, CORS, WebSocket, PostMessage와 같은 새로운 표준들이 등장했습니다. 여기에 권한 부여와 상태 없는 인증을 위한 OAuth2 및 JSON 웹 토큰(JWT)과 같은 새로운 표준들이 결합되면서, 현대적인 웹 API는 갑자기 브라우저에서 실행되는 모든 자바스크립트 클라이언트에서 접근할 수 있게 되었습니다.

우리는 아주 최근에야 이 거대한 혁신의 효과를 이해하기 시작했습니다. 이것은 JAMstack을 웹사이트와 애플리케이션을 위한 가장 적절한 아키텍처 스타일 중 하나로 추진하는 원동력 중 하나입니다. 갑자기 모든 웹이 거대한 운영체제처럼 변했습니다. 이제 우리는 대규모 클라우드 환경에서 실행되는 고급 머신 러닝 모델을 통한 결제나 구독부터, 배송이나 차량 공유 서비스처럼 물리적 세계에 직접 영향을 미치는 서비스, 그리고 상상할 수 있는 거의 모든 것에 대해 API가 노출되는 것을 보고 있습니다. 생각해 낼 수 있다면, 아마 어딘가에 그에 대한 API가 존재할 것입니다.

#### 마크업 (Markup)

웹의 핵심에는 HTML이 있습니다. 모든 브라우저가 알고 이해하는 하이퍼텍스트 마크업 언어(HyperText Markup Language)는 콘텐츠가 어떻게 구조화되고 배포되어야 하는지를 정의합니다. 사이트를 위해 어떤 리소스와 자산을 로드해야 하는지를 정의하고, 표준 웹 브라우저에서부터 스크린 리더, 검색 엔진 크롤러, 음성 제어 장치나 스마트 워치에 이르기까지 모든 것이 파싱하고, 표현하고, 처리할 수 있는 문서 객체 모델(DOM)을 제시합니다.

웹의 초기 시절, 웹사이트는 단순히 웹 서버가 HTTP를 통해 노출하는 HTML 파일이 담긴 폴더였습니다. 웹이 진화함에 따라, 우리는 서버에서 실행되는 프로그램이 방문할 때마다(보통 데이터베이스를 조회한 후) 즉석에서 HTML을 빌드하는 모델로 이동하기 시작했습니다.

이것은 정적 자산을 제공하는 것보다 훨씬 느리고 복잡한 과정이었지만, 당시 브라우저가 단순한 문서 뷰어에 불과했다는 사실을 우회할 수 있는 유일한 실행 가능한 방법이기도 했습니다. 클릭이나 양식 제출과 같은 사용자 상호작용에 응답하려면 서버에서 완전히 새로운 HTML 페이지를 조립해야 했습니다. 이는 블로그의 댓글 기능이든, 이커머스 스토어든, 어떤 종류의 웹 애플리케이션을 구축하든 마찬가지였습니다. 이러한 문서 중심 아키텍처 때문에 웹 경험은 종종 데스크톱 애플리케이션보다 반응성이 훨씬 떨어지는 것처럼 느껴졌습니다.

물론 이것은 자바스크립트의 부상과 브라우저에서 사용 가능한 크로스 도메인 웹 API가 등장하기 전의 이야기입니다. 오늘날에는 웹의 레거시 아키텍처를 초래했던 제약 조건들이 사라졌습니다.

#### 마크업 미리 빌드하기 (Prebuilding Markup)

JAMstack에서 마크업은 다른 모델로 전달됩니다. 런타임에 페이지를 빌드하는 작업을 수행하는 전통적인 프론트엔드 웹 서버에서 전달되지 않습니다.

대신 JAMstack의 접근 방식은 모든 마크업을 사전에 빌드하고 CDN에서 브라우저로 직접 제공(serve)하는 것입니다. 이 과정은 일반적으로 콘텐츠와 템플릿이 HTML로 결합되고, 소스 파일이 자바스크립트로 트랜스파일되거나 컴파일되며, CSS가 전처리기나 후처리기를 거치는 빌드 도구(때로는 Hugo나 Gatsby 같은 정적 사이트 생성기, 때로는 Webpack, Brunch, Parcel 같은 프론트엔드 빌드 도구)를 포함합니다.

이것은 프론트엔드와 모든 백엔드 API 사이에 엄격한 분리(decoupling)를 만듭니다. 이를 통해 인프라와 라이브 시스템에서 움직이는 많은 부품을 제거할 수 있으며, 이는 관련된 프론트엔드와 개별 API를 독립적으로 고려하는 것을 훨씬 쉽게 만듭니다. 우리가 사이트의 콘텐츠 계층을 주문 즉시 조리(fry)하는 것이 아니라 **미리 구워(bake) 낼수록**, 배포, 확장, 보안은 더 단순해지고 성능과 최종 사용자 경험은 더 좋아질 것입니다.

여러 면에서 이 분리된 아키텍처는 모바일 앱의 아키텍처와 유사합니다. 아이폰이 모바일 앱을 도입했을 때(원래는 전통적인 웹 앱의 성능이 충분하지 않았기 때문입니다), 사용자가 어떤 행동을 취할 때마다 서버에서 전체 UI를 다시 로드하는 모델을 구축하는 것은 고려조차 되지 않았습니다. 대신 iOS는 각 앱이 선언적 UI를 갖춘 애플리케이션 패키지로 사용자에게 배포되고, 여기에는 JSON 또는 XML 기반 웹 API와 통신하는 데 필요한 모든 자산이 포함되는 모델을 도입했습니다.

JAMstack의 접근 방식도 유사합니다. 프론트엔드가 곧 앱입니다. 이는 전 세계적으로 분산된 네트워크상의 CDN에서 브라우저로 직접 배포됩니다. 서비스 워커(service workers) 같은 기술을 통해 우리는 사용자의 첫 방문 이후 프론트엔드를 최종 사용자의 기기에 직접 설치할 수도 있습니다.

#### 마이크로서비스와 서버리스 함수

프론트엔드와 API 계층을 분리하기 시작한 것과 동시에 또 다른 일이 일어났습니다. 바로 마이크로서비스 기반 아키텍처입니다. 백엔드 팀은 하나의 거대한 모놀리식 API에서 벗어나 더 좁게 정의된 책임을 가진 훨씬 작은 서비스들로 이동하기 시작했습니다. 이러한 마이크로서비스로의 이동은 아마존 웹 서비스(AWS) 람다(Lambda)와 클라우드 함수(cloud functions) 개념에서 정점에 달했습니다. 이를 통해 딱 한 가지 일만 수행하고 그 외에는 아무것도 하지 않는 단순한 함수들이 마이크로 웹 API 엔드포인트로 노출될 수 있게 되었습니다.

이는 중요한 아키텍처적 변화를 촉발했습니다. 이전에는 전형적인 SPA가 통신할 API가 단 하나뿐이었습니다. 이제 각 SPA는 일반적으로 서로 다른 많은 API나 마이크로서비스와 통신하게 됩니다. 이러한 각 API의 표면적(surface area)이 줄어들고 OAuth나 JWT 같은 표준이 개발자들로 하여금 이들을 서로 연결할 수 있게 함에 따라, 개별 API는 점점 더 재사용 가능해지는 경향이 있습니다.

관리형 서비스(managed services)로서 사용 가능한, 완전히 관리되고 재사용 가능한 API의 양은 계속해서 증가할 것입니다. 우리는 이제 현대적인 애플리케이션 운영에 관련된 유지 관리의 부담을 덜어주는 최초의 '함수 앱 스토어(function app stores)'들을 보기 시작했습니다.

### JAMstack 프로젝트의 유형

전 세계의 개발 팀들은 작은 사이트와 랜딩 페이지부터 복잡한 웹 애플리케이션, 수천 페이지에 달하는 대규모 기업 웹 자산에 이르기까지 다양한 JAMstack 기반 프로젝트를 배포해 왔습니다.

#### HTML 콘텐츠

가장 단순한 JAMstack 사이트는 순수 정적 사이트입니다. HTML과 지원 자산(자바스크립트, CSS, 이미지, 폰트 파일)이 담긴 폴더 하나로 구성되며 움직이는 부품이 없습니다. 이는 선호하는 에디터에서 직접 편집하고 버전 관리 하에 둘 수 있는 일반 텍스트 파일들입니다.

하지만 페이지가 하나 이상으로 늘어나면 내비게이션, 헤더, 푸터, 반복되는 요소들을 템플릿과 부분(partials)으로 추출하는 것이 합리적입니다. 가장 단순한 자바스크립트를 제외하고는 npm에서 모듈을 가져와 더 현대적인 ES6 기능을 사용할 수 있습니다. 스타일시트가 조금 더 복잡해지면 필요할 때 자동 벤더 접두사(vendor prefixing) 추가, 브라우저 간 CSS 변수 지원, 규칙 중첩 등을 도입할 수 있습니다.

적절한 빌드 도구 체인은 정적 사이트의 기본적인 단순함을 유지하면서 이 모든 문제를 해결해 줍니다. 모든 것은 Git 저장소의 텍스트 파일에 존재하고, 버전 관리되며, 텍스트 중심의 모든 개발자 도구로 조작할 수 있습니다. 현대적인 지속적 배포(CD) 워크플로를 사용하면, 배포는 'Git push'만큼이나 간단해집니다.

#### CMS의 콘텐츠

웹 역사의 대부분 동안, 우리는 CMS가 전체 개발 플랫폼을 결정하고 렌더링, 콘텐츠 편집, 플러그인 생태계를 긴밀하게 결합한다는 것을 당연하게 여겼습니다. 하지만 **헤드리스 CMS(headless CMSs)**—그것이 API 기반이든 Git 기반이든—의 출현은 우리가 콘텐츠 편집 UI를 웹사이트 렌더링 및 제공 도구와 완전히 분리된 것으로 생각할 수 있음을 의미합니다.

콘텐츠 관리는 Netlify CMS, Prose, Forestry, CloudCannon 같은 Git 중심의 콘텐츠 편집 도구로 처리할 수도 있습니다. 또는 빌드 도구를 사용하여 첫 번째 빌드 단계에서 Contentful, Prismic, DatoCMS 같은 외부 콘텐츠 API와 콘텐츠를 동기화할 수도 있습니다.

#### 웹 애플리케이션

2000년대 초, 마이크로소프트는 인터넷 익스플로러(Internet Explorer)에 XMLHttpRequest(XHR)라는 자체 개발 API를 조용히 추가했습니다. 이 전까지 브라우저가 페이지 로드를 시작할 수 있는 유일한 방법은 완전히 새로운 웹 페이지를 처음부터 로드하는 새로운 URL로 이동하는 것뿐이었습니다.

XHR이 거의 주목받지 못한 채 몇 년이 지난 후, 2005년 2월 에이전시 어댑티브 패스(Adaptive Path)의 제시 제임스 개럿(Jesse James Garrett)은 웹을 변화시킬 "Ajax: 웹 애플리케이션에 대한 새로운 접근 방식"이라는 글을 썼습니다. 이 글에서 제시는 "Ajax"라는 용어를 만들었고, 웹 개발자들에게 자바스크립트에서 직접 서버로부터 데이터를 가져오기 위해 XHR이 사용된 후 등장한 새로운 패턴에 대해 소통할 방법을 제공했습니다. 이는 현재 JAMstack이라는 용어가 통일된 명명법의 기치 아래 새로운 아키텍처에 대해 이야기할 수 있게 해주는 것과 유사합니다.

프론트엔드 비중이 높은 웹 애플리케이션이 어디에나 존재하는 오늘날의 세상에서는, 웹 애플리케이션과 진정으로 상호작용하는 유일한 방법으로서 전체 페이지 새로고침에 의존하던 것에서 자바스크립트에서 직접 HTTP 요청을 시작할 수 있는 옵션을 갖게 된 것이 얼마나 혁명적인 일이었는지 실감하기 어렵습니다. 전체 페이지 로드에 의존하지 않고 Ajax 요청을 사용하여 웹 애플리케이션을 구축할 수 있다는 사실은 우리가 웹에 대해 생각하는 방식을 바꾸었으며, 브라우저 시장이 수년간의 IE6 기반 침체기에서 벗어나 근본적으로 스스로를 재창조하기 시작하도록 밀어붙였습니다.

처음에 Ajax는 주로 점진적 향상(progressive enhancement) 원칙과 함께 사용되었습니다. 웹 애플리케이션은 모든 상태가 전체 페이지 전환을 통해 서버에서 처리되는 방식으로 구축되지만, 자바스크립트를 지원하는 브라우저는 부분적인 페이지 새로고침을 통해 상호작용을 향상할 수 있는 방식이었습니다.

#### 프론트엔드와 백엔드의 분리

진정한 SPA는 자바스크립트 성능이 충분히 좋아져서 기존 모델을 뒤집고 서버 측 왕복 없이 브라우저에서 모든 페이지 전환을 직접 처리할 수 있게 되었을 때 등장했습니다. 1세대 SPA는 일반적으로 거대한 모놀리식 데이터베이스 기반 애플리케이션 내부에서 프론트엔드를 개발하는 방식으로 구축되었습니다. Rails 앱 내부에서 Ember 프론트엔드로 작업하며 번들링과 축소(minification)를 위해 Rails 자산 파이프라인을 사용하는 것이 일반적이었습니다(비록 이 흐름은 작업하기에 대부분 고통스러웠지만 말입니다).

현대적인 SPA는 프론트엔드와 백엔드를 완전히 분리하기 시작했고, 프론트엔드를 독립적으로 작업하는 것을 진정으로 즐겁게 만들어주는 새로운 세대의 프론트엔드 빌드 도구들이 등장했습니다(물론 초기 설정과 구성의 장애물을 극복한 후에 말이죠). 오늘날 SPA에 가장 널리 사용되는 빌드 도구인 Webpack은 자바스크립트 및 CSS 트랜스파일링, 후처리, 통합 번들링 및 코드 분할, 그리고 저장 시 실시간 브라우저 새로고침을 지원하는 흐름을 제공합니다.

#### 대규모 웹 자산

마크업을 미리 빌드하는 것에 있어서, 생성하기에 실용적인 페이지 수 측면에서 명백한 제약이 존재합니다. 빌드 및 배포 주기가 너무 길어지면 실행 가능한 워크플로가 불가능해집니다. 경쟁자보다 먼저 기사를 발행해야 하는데, CMS에서 '발행'을 누른 순간부터 기사가 라이브 되기까지 1시간의 빌드 및 배포 주기가 걸린다면, 스택이 근본적으로 여러분을 실망시킨 것입니다.

일부 퍼블리싱 유형에서는 이것이 매우 엄격한 제약 사항이어서 10분의 빌드 및 배포 주기조차 다른 스택으로 작업하는 것이 나을 수 있습니다.

하지만 빌드 도구들은 놀라울 정도로 빨라졌고, 빌드 주기로 달성할 수 있는 한계는 줄어들고 있습니다. Hugo 같은 정적 사이트 생성기는 초당 수천 페이지를 처리하며 훨씬 빠른 빌드 주기를 제공할 수 있습니다. 이러한 도구들의 인상적인 성능 향상과 더불어, 각 업데이트에 대해 사이트의 작은 부분만 다시 빌드하도록 사이트 생성을 별도의 브랜치로 신중하게 분할하여 초대형 사이트를 다루는 새로운 기술들이 결합되어 훌륭한 결과를 제공합니다.

결국, 트레이드오프는 가장 중요한 것이 무엇인가에 기반해야 합니다. 성능, 가동 시간(uptime), 확장성인가, 아니면 퍼블리싱 주기의 단축인가 하는 점입니다.

대부분의 콘텐츠 중심 사이트의 경우, 배포가 특정 시간에 라이브 되도록 예약될 수만 있다면 빌드 주기를 10분 이내로 실행하는 것은 실제로는 별로 중요하지 않을 수 있습니다. 사이트가 정말로 거대하지 않다면(페이지 수가 수천 개가 아니라 수백만 개 단위가 아니라면), JAMstack 접근 방식은 여러분이 한때 생각했던 것보다 훨씬 더 실행 가능한 옵션일 수 있습니다.

#### 하이브리드 경험

기업이 다양한 웹 경험을 필요로 하는 것은 흔한 일입니다. 메인 웹사이트, 블로그, 문서 사이트, 웹 애플리케이션, 이커머스 스토어 등이 필요할 수 있습니다. 과거 웹 팀들에게 이 모든 애플리케이션에 걸쳐 공통된 룩 앤 필(look and feel)을 유지하는 것은 매우 어려운 일이었습니다. 전통적인 아키텍처에서는 각 애플리케이션의 프론트엔드가 서버에서 이를 생성하는 데 사용되는 백엔드와 강하게 결합되어 있었기 때문입니다.

JAMstack은 이 문제를 우아하고 확장성 높은 방식으로 해결합니다. 우리는 모든 애플리케이션에 걸쳐 있는, 분리된 하나의 프론트엔드를 구축할 수 있습니다. 나중에 스매싱 매거진(Smashing Magazine) 사례 연구를 소개할 때 이것이 실제로 어떻게 작동하는지 보게 될 것입니다.

#### 요약

JAMstack 아키텍처에 적합하지 않은 프로젝트의 목록은 지속적으로 줄어들고 있습니다. 도구와 자동화, 워크플로, 모범 사례, 그리고 전체 생태계의 개선은 JAMstack 사이트가 달성할 수 있는 가능성을 더 많이 만들어내고 있습니다.

이제 JAMstack이 무엇인지, 그리고 여러분의 프로젝트에 적합한지 다루었으니, JAMstack 접근 방식이 제공할 수 있는 이점들에 대해 이야기할 차례입니다.
